## Goal
Every application records where the role came from, how it was submitted, when it was submitted, when the first reply
came and how it ended. Today these are scattered across `jobs.source`, `applications.applied_at`, `applications.status`
and `application_events`. Plain columns let outcome analytics (8.4: interviews per 100 applications by source, role,
country and CV variant, time to first reply) and the weekly review stay simple and honest.

## What to build
1. **Vocabulary** (`src/lib/outcomes.ts`, new): typed lists with plain labels.
   - `source`: `ats_feed` (jobs.source `greenhouse`, `lever`, `ashby`, `workday`), `career_page` (`career_page`,
     `career_pages`), `alert_email` (`linkedin`, `indeed` and other alert kinds from `gmailSync.server.ts`), `pasted_text`
     (`pasted`), `referral` (set by the user only), `manual` (`manual`, `direct`, anything else).
   - `submit_channel`: `employer_form`, `employer_api`, `extension`, `email`, `other`. Null means unknown.
   - `outcome`: `offer_accepted`, `offer_declined`, `rejected`, `withdrawn`, `no_response`. Null means still open.
   Role- and country-agnostic; no board is a "channel" (job boards are never automated, AGENTS.md).
2. **Submitted time**: reuse `applications.applied_at` (already set by `move()` in `applications.tsx`, the detail page and
   `gmailSync.server.ts`). Do not add a second "submitted_at" column.
3. **Source on insert**: a database trigger fills `applications.source` from the job when the insert leaves it null, so
   `radar.tsx`, `portal.tsx`, `synthesizePack` and the Gmail sync need no change. The user can change it to `referral`
   (with an optional `referral_note`) on the detail page.
4. **First reply**: a trigger on `application_events` insert sets `applications.first_reply_at` to the earliest event
   time whose `event_type` is in `RESPONSE_EVENTS` (export the set from `src/lib/insights.ts`; the SQL list must match it).
   This keeps it in step with every writer (Gmail sync, review queue, manual linking). The Today view stays derived from
   events (AGENTS.md); these columns are a summary for analytics, never edited by hand.
5. **UI**: when the user marks an application applied (`move()` and the detail page), an optional "How did you apply?"
   choice sets `submit_channel`; leaving it blank keeps null. On the detail page, show source, channel, applied and
   first-reply dates, and an outcome picker that sets `outcome` and `outcome_at`; setting `rejected` there also sets
   `status` to `rejected`, and status `rejected` from email sets `outcome` too (same trigger or one update). Write an
   `application_events` row for each change, as `move()` does today.
6. **Export and delete**: no new table; the new columns ride along with `applications` in `exportMyData`. Check the
   export test or add one assertion that the columns are present.

## Database
New `supabase/migrations/<yyyymmddhhmmss>_application_outcomes.sql`: on `applications` add `source text`,
`referral_note text`, `submit_channel text`, `first_reply_at timestamptz`, `outcome text`, `outcome_at timestamptz`, each
with a check constraint for the lists above (null allowed). Functions (plain `plpgsql`, `set search_path = public`, not
security definer): `application_source_for_job(text)` and the two triggers. Index `(user_id, source)`.
Backfill, in the same migration, in this order: `source` from the job via `application_source_for_job`; `applied_at`
where null from the earliest `submitted` event; `first_reply_at` from the earliest response event per application;
`outcome = 'rejected'`, `outcome_at = updated_at` where `status = 'rejected'`; `submit_channel` stays null (unknown; never
guessed). Regenerate types with `bun run db:types` (or hand-edit and say so in the PR).

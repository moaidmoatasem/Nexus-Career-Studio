## Goal
A self-hoster can turn on live Gmail updates by copying a short, checked list of `gcloud` commands, instead of
translating today's prose paragraph into console clicks. New recruiter mail then reaches the app within about a minute
rather than at the next 15-minute agent run.

## Prior art to check first
None found: career-ops has no Gmail feed yet (its issue #1583, Track A.1), and JobSync has no inbox tracking.

## What to build
1. **Check the PLAN.md 4.1 commands against Google's current docs** before copying them:
   Gmail push (https://developers.google.com/workspace/gmail/api/guides/push), Pub/Sub push authentication
   (https://cloud.google.com/pubsub/docs/authenticate-push-subscriptions) and `gcloud pubsub subscriptions create`.
   Confirm at least:
   - the publisher principal is still `serviceAccount:gmail-api-push@system.gserviceaccount.com`, and the topic must be
     in the same Google Cloud project as the OAuth client (`GOOGLE_CLIENT_ID`); note that a Workspace organisation's
     "domain restricted sharing" policy can block that binding;
   - `--push-auth-service-account` with no `--push-auth-token-audience` makes the token audience the push endpoint URL,
     which is exactly what `expectedPushAudience` in `src/lib/gmailPushAudience.ts` expects (`$APP_URL/api/public/gmail-push`);
   - whether the Pub/Sub service agent (`service-<project-number>@gcp-sa-pubsub.iam.gserviceaccount.com`) still needs
     `roles/iam.serviceAccountTokenCreator` on the push service account (Google required it for older projects), and
     that the person running the command needs `iam.serviceAccounts.actAs` on it. Add the binding if the docs still
     call for it;
   - the push acknowledgement deadline. `src/routes/api/public/gmail-push.ts` answers only after
     `syncGmailForUser(userId, 25)` finishes, which can take longer than Pub/Sub's default 10 s and cause redelivery.
     Add `--ack-deadline=60` (or the value the docs justify) to the subscription command and say why in one line.
2. **Rewrite the "Automatic updates (optional)" paragraph of DEPLOY.md section 5** as numbered steps: the checked
   commands (with `P=<project-id>` and `<domain>` placeholders), then the two `.env` lines from PLAN.md 4.2
   (`GMAIL_PUBSUB_TOPIC=projects/<project-id>/topics/nexus-gmail`,
   `GMAIL_PUBSUB_SERVICE_ACCOUNT=nexus-gmail-push@<project-id>.iam.gserviceaccount.com`), the restart, and how to check:
   `/api/public/health` shows `gmailLiveUpdates: true` (`checkConfiguration` in `src/server/agentRunner.server.ts`); the
   next agent run or reconnecting Gmail calls `registerGmailWatch` (`src/server/gmailSync.server.ts`), and the agent
   renews the 7-day watch within 24 h of expiry (`renew_gmail_watch` in the activity log). Keep the existing sentences on
   `GMAIL_PUBSUB_AUDIENCE` (only if the subscription uses a custom audience) and the fallback to scheduled checks.
3. **Mark the section "Unverified until PLAN.md 4.3"**: no deployment exists yet, so say plainly the commands have
   not been run end to end.
4. **Env vars.** The code reads `GMAIL_PUBSUB_TOPIC`, `GMAIL_PUBSUB_SERVICE_ACCOUNT` and `GMAIL_PUBSUB_AUDIENCE`, and
   uses `APP_URL`; all four are already in `.env.example`. Only touch `.env.example` to add a one-line comment for
   `GMAIL_PUBSUB_SERVICE_ACCOUNT` (the push service account's email). No code changes: if the docs show the route needs
   anything else, stop and ask in the PR instead of changing `gmail-push.ts`.
5. If `gcloud` in the session is signed in to the owner's project (it normally is not), do not run the commands in this
   task: running them is 4.2/4.3 with the owner.

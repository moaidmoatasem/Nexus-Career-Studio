## Goal
A user can keep several versions of their CV (for example "Data analyst" and "Operations lead"), each a chosen, ordered
selection of their **verified** Career Vault items with its own headline and export format. Each search profile (5.1)
and each application can point at one, so exports, tailoring and later outcome analytics (8.4) know which CV was used.
It is also what 10.6 (Arabic and English CVs) builds on.

## What to build
1. **Model builder** (`src/lib/cvVariants.ts`, new): move the `ResumeModel` construction out of `resume.tsx` (lines ~38–80:
   verified filter, experience/project vs education/certification split, `bulletsFor`) into a pure
   `buildResumeModel({ profile, vault, variant, pack })`. Rules: only `is_verified` items are ever used; with
   `include_all_verified` the variant behaves exactly like today's resume page; otherwise only its listed items, in its
   order. Listed items that are now unverified or deleted are dropped and returned as `warnings`, never rendered.
2. **No new claims**: a variant holds selections, order, a user-written headline and a format, nothing generated. Tailored
   bullets still come only from `tailored_pack`, which already passed `validateBulletProvenance` in `synthesizePack`. If
   you add any generated text (for example a summary), it must pass `auditFreeText` from `src/lib/provenance.ts` with
   `evidenceNumbers` built from the variant's items, exactly as cover letters do.
3. **Exports** (`src/lib/resumeExport.ts`): `downloadPdf`, `downloadDocx`, `toPlainText` and `downloadProvenanceReport` take
   the model from `buildResumeModel`; the variant's `ats_format` (`generic`, `workday`, `lever`, the existing `AtsProfile`
   keys) is the default choice. Name the file after the variant (`fileBase`). Note: `PROFILES` there means ATS formats,
   not search profiles; rename it to `ATS_FORMATS` while you own the file.
4. **Tailoring** (`synthesizePack`): optional `cvVariantId`; when given, the vault passed to the prompt and to
   `validateBulletProvenance` is the variant's verified items only, and the application stores `cv_variant_id`.
   Without it, behaviour is unchanged (default variant or all verified items).
5. **UI**: on `resume.tsx`, a variant picker (create, rename, duplicate, delete, set default) and `CvVariantEditor.tsx` to
   pick and reorder verified items (unverified items appear greyed with "verify in Career Vault first"). Show warnings
   from step 1. Keep it usable on a phone. A `useCvVariants()` hook in `src/lib/data.ts`.
6. **Data export and delete** (`src/lib/account.functions.ts`): add `cv_variants` and `cv_variant_items` to `OWN_TABLES`;
   delete `cv_variant_items` before `cv_variants`, and both before `vault_items`.

## Database
New `supabase/migrations/<yyyymmddhhmmss>_cv_variants.sql`:
- `cv_variants`: `id`, `user_id`, `name`, `headline text not null default ''`, `ats_format text` (check `generic`, `workday`,
  `lever`), `language text not null default 'en'` (BCP 47, for 10.6), `include_all_verified bool not null default false`,
  `is_default bool`, timestamps with `set_updated_at`. Partial unique index: one default per user. RLS like `role_decisions`.
- `cv_variant_items`: `variant_id` (FK, on delete cascade), `vault_item_id` (FK to `vault_items`, on delete cascade),
  `user_id`, `position int`, primary key `(variant_id, vault_item_id)`. Policy: `auth.uid() = user_id` and both the variant
  and the vault item belong to `auth.uid()` (an `exists` check, like the `portal_tasks` insert policy).
- `applications.cv_variant_id uuid` references `cv_variants` on delete set null (5.4 and 8.4 read it).
- Backfill: one variant "Main CV" (`include_all_verified = true`, `is_default = true`, `headline` from `profiles.headline`)
  for every user with at least one vault item; existing applications keep `cv_variant_id` null.
Regenerate types with `bun run db:types` (or hand-edit and say so in the PR).

## Goal
Users targeting the Netherlands, Canada or the US see, for each employer, what the official public data says (with its
source and date) and refresh it on a schedule, the way the UK register works today.

## Prior art to check first
career-ops `plugins/h1b-sponsor` already covers US H-1B data. Reuse its source choice and parsing (MIT, keep the notice)
or contribute NL and CA there first if the owner prefers (Track A). Say which in the PR.

## What to build
1. **First PR: sources only.** For each country, propose the official source, its URL, publisher, format, update frequency,
   licence or terms, and whether automated download is allowed. Candidates to verify: the IND public register of recognised
   sponsors (Netherlands); ESDC's positive LMIA employers list on open.canada.ca (Canada, Open Government Licence); the USCIS
   H-1B Employer Data Hub (United States; DOL OFLC disclosure data as an alternative). Write it to `docs/visa-sources/registers.md` and
   stop for the owner's review. Only official sources; no scraping where terms forbid it; never a third-party mirror.
2. Wording reflects what each list means: NL "recognised sponsor", CA "had a positive LMIA in <quarter>", US "H-1B petitions
   approved in FY<year>". Only NL is a licence; CA and US are history, not a promise. Put the wording in each module.
3. Modules `src/lib/visa/{nl,ca,us}.ts` implement `VisaModule` (9.1): `checkEmployer` calls the new RPC below and returns
   listed / possible / not_listed with the entry, similarity and snapshot date.
4. Refresh `src/server/visa/{nl,ca,us}.server.ts`: download, parse, checksum (Web Crypto, as `sponsorRefresh.server.ts`
   does), stage, then activate. Reuse `parseCsv` and `normalizeCompany` (moved by 9.1); per-country legal-suffix lists
   (B.V., N.V., Inc., LLC, Ltd., Corp.) live in each module. Register them with 9.1's refresh loop in `agentRunner.server.ts`
   (one `claim_automation_job` key each) with a schedule per source (for example weekly NL, quarterly CA, yearly US).
   A failed download keeps the previous snapshot active and logs the error; it never empties a register.

## Database
New migration (do not touch the UK `sponsors` tables or `match_sponsor_company_v3`):
- `visa_register_snapshots` (id, country, source_url, source_published_at, checksum, row_count, status, error_summary,
  timestamps) and `visa_register_entries` (snapshot_id, country, organisation_name, organisation_normalized, attributes jsonb),
  with a pg_trgm GIN index on `organisation_normalized` and a btree on (country, organisation_normalized).
- RLS: public read of active snapshots' rows (like `sponsor_snapshots`); writes by service_role only.
- `match_visa_register(country text, search_term text, threshold real default 0.35, max_results int default 10)`, stable,
  modelled on `match_sponsor_company_v3`; `activate_visa_snapshot(uuid)` security definer, service_role only, with a
  per-country minimum row count, modelled on `activate_sponsor_snapshot`.
- Run `bun run db:types`; extend `src/test/migrations.test.ts` (PGlite replay, RPC returns an exact match first).

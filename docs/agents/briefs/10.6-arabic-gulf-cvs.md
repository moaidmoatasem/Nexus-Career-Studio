# 10.6 Arabic and English CVs, and a Gulf CV template

**State:** gate-1 · **Needs:** 10.1, 10.3 and 10.4 merged; coordinate with 5.2 (CV variants) if it is open or merged. Last task of Phase 10.
**File area:** `src/lib/resumeExport.ts`, `src/routes/_authenticated/resume.tsx`, `src/lib/cv/**` (new), `.ats-paper` rules in `src/styles.css`, `supabase/migrations/<new>_cv_personal_fields.sql` (new), `src/integrations/supabase/types.ts`, `src/test/resumeExport.test.ts` (new), `src/test/migrations.test.ts`
**Branch:** `agent/10.6-arabic-gulf-cvs` · **PLAN.md:** [10.6](../../../PLAN.md#phase-10-arabic-first-interface-gate-1)

## Goal
A user applying in the Gulf can download a correct right-to-left Arabic CV and an English one, and choose a Gulf layout
with the optional fields employers there often expect, without the app ever inventing a claim.

## Prior art to check first
career-ops ships Arabic CV and cover-letter modes, including Gulf terms. Read them first; reuse their section names and
wording (MIT, keep the notice), and offer the Gulf template upstream as STRATEGY.md's Track A suggests.

## What to build
1. Model: extend `ResumeModel` in `src/lib/resumeExport.ts` with `lang: "en" | "ar"` (taken from 5.2's `cv_variants.language`
   when 5.2 has merged) and optional `personal`
   (`nationality`, `visaStatus`, `currentLocation`, `noticePeriod`; anything else only if the owner adds it). A Gulf
   template in `src/lib/cv/templates.ts` (new) orders sections and shows these fields; generic and ATS templates
   (`PROFILES`: generic, workday, lever) never show them.
2. Arabic Word export first: in `downloadDocx`, for `lang: "ar"` set `bidirectional: true` on paragraphs, `rightToLeft: true`
   on text runs, a complex-script font (`font: { cs: … }`) and the Arabic language tag; Word does the shaping. English output
   must stay byte-identical.
3. PDF: `downloadPdf` uses pdfmake with its default Roboto fonts, which have no Arabic glyphs and no shaping. Keep PDF disabled
   for Arabic with a clear message ("Download Word for Arabic CVs") until a renderer is proven: test pdfmake and
   `@react-pdf/renderer` (already a dependency) with real Arabic text, ligatures and mixed English words, and attach the
   PDFs to the PR. Enable Arabic PDF only if one shapes correctly; otherwise record why in PLAN.md.
4. Arabic content comes from the user's own Arabic vault items or Arabic text the user edits. If an AI translation step is
   added, it goes through `generateStructured` in `src/lib/ai.functions.ts` and every translated bullet passes
   `validateBulletProvenance`. Check first that `numbersIn` in `src/lib/provenance.ts` reads Arabic-Indic (٠–٩) and Persian
   digits; on 2026-10-08 it did not (its `\d` matches ASCII only), so normalise them to ASCII before comparing.
5. `resume.tsx`: language and template pickers; the preview (`.ats-paper`, which names "Amiri" without loading it) uses
   `dir="rtl"` and the 10.3 font for Arabic.
6. Personal data: all Gulf fields optional and empty by default, entered only by the user, included in Settings export and
   account deletion (`src/lib/account.functions.ts`), and never sent to an AI provider.

## Database
New migration: optional nullable columns on `profiles` (`nationality`, `visa_status`, `current_location`, `notice_period`),
covered by the existing own-row RLS; or, if 5.3 (answer bank) has merged, read them from there instead and add no columns.
Run `bun run db:types`; extend `src/test/migrations.test.ts`.

## Tests
`src/test/resumeExport.test.ts` (new): the Arabic docx has RTL paragraph and run properties (unzip `word/document.xml`);
English output is unchanged; Gulf fields appear only in the Gulf template and only when filled; PDF for Arabic is refused
until enabled. `src/test/provenance.test.ts`: an Arabic-digit metric not in the vault is rejected.

# 13.1 Import a "Download my data" export file

**State:** waiting-on-owner-ask · **Needs:** the owner asks for Phase 13.1; a sample export from 0.1b helps
**File area:** new `src/lib/import.functions.ts`, new `src/lib/importExport.ts` (pure parsing/mapping),
`src/routes/_authenticated/settings.tsx` (an import card), new `src/test/importExport.test.ts`; `src/lib/account.functions.ts` only for step 5
**Branch:** `agent/13.1-import-lovable-export` · **PLAN.md:** Phase 13, task 13.1

## Goal
Someone moving from the old Lovable-hosted copy keeps their Career Vault, applications and history by uploading the
JSON from **Settings → Download my data**, instead of retyping it. Running the import twice never duplicates anything.

## Prior art to check first
career-ops and JobSync have no importer for this format (none found). JobSync's own import/export is a different
schema; nothing to reuse.

## What to build
1. **Learn the export shape** from `exportMyData` in `src/lib/account.functions.ts`: a JSON object with `exported_at`,
   `user_id`, `profile` (one `profiles` row or null), one array per table in `OWN_TABLES` (`vault_items`, `applications`,
   `application_events`, `role_decisions`, `source_connections`, `discovery_runs`, `agent_settings`, `agent_activity`,
   `portal_tasks`, `unmatched_mail_messages`, `processed_mail_messages`) and `jobs_added_by_you` (private `jobs` rows).
   Column types are in `src/integrations/supabase/types.ts`. The Lovable build may predate later migrations: the zod
   schemas in `src/lib/importExport.ts` accept unknown extra keys (strip them) and treat columns added by later
   migrations as optional.
2. **Known gap:** applications and role decisions point at `job_id`, but catalog jobs (`user_id` null) are not in the
   export, so their `canonical_url` is unknown. Import only links that can be resolved (private jobs from
   `jobs_added_by_you`, or a `job_id` whose catalog row already exists here); report the rest as "skipped: job not in
   the export" with the count. Do not invent job fields (AGENTS.md: inaccessible pages never produce invented data).
3. **Pure mapping** in `src/lib/importExport.ts`: build an old-id → new-id map per table with `crypto.randomUUID()` (Web
   Crypto, no Node built-ins), rewrite foreign keys (`applications.job_id`, `application_events.application_id/job_id`,
   `role_decisions.job_id`, `portal_tasks.application_id`, `agent_activity.application_id`,
   `unmatched_mail_messages.linked_application_id`, `processed_mail_messages.application_id`), set `user_id` to the
   caller, and reuse an existing job by `canonical_url` (catalog first, then the user's own; unique indexes in
   `20261005174721_…sql`).
4. **Idempotent writes** in `src/lib/import.functions.ts`: an auth-protected `createServerFn` with
   `requireSupabaseAuth`, input validated with zod, size-capped (say 10 MB). Rely on the existing unique keys
   (`applications (user_id, job_id)`, `role_decisions (user_id, job_id)`, `source_connections (user_id, source)`,
   mail `(user_id, provider, provider_message_id)`) with upserts that ignore duplicates, and match vault items and
   events on content + timestamp so a second run inserts nothing. Use the caller's RLS client, not the service role.
   Skip `portal_tasks` (their screenshots do not exist here); import `agent_activity` as history; `profile` fills only
   empty fields. Gmail tokens are not exported, so users reconnect Gmail.
5. Return a summary per table (imported, already present, skipped with reason) and show it in a Settings card next to
   **Download my data**. Imported text is untrusted data: it is stored, never sent to the AI provider by the import.

## Database
None expected. If an idempotency key is missing (for example on `vault_items`), add a migration with a unique index
on a content hash, extend `src/test/migrations.test.ts`, and regenerate the types (`bun run db:types`).

## Tests
`src/test/importExport.test.ts` (`// @vitest-environment node`) on a PGlite fixture built like `migrations.test.ts`:
a fixture export (made-up data) imports with links intact; a second import adds nothing; a catalog job is reused by
`canonical_url`; an application whose catalog job is missing is skipped and reported; extra unknown keys are ignored;
an export for another `user_id` imports into the caller's account only.
